# Evaluation report

This report covers three evaluations: retrieval (dense vs hybrid), chunking (paragraph vs fixed) and answers (simple vs agent mode). Every number below is copied from a file in `eval/results/`. The file is named under each table.

## 1. Setup

**Retrieval set.** `eval/retrieval_questions.jsonl`: 200 questions from the HotpotQA distractor validation split, picked with seed 42 by `scripts/build_hotpot.py`. 170 are bridge questions and 30 are comparison questions. Every question has 2 gold documents: the titles in its `supporting_facts`. Both configurations search the full local database and return the top 10 chunks.

**Chunking subset.** The context paragraphs of those 200 questions: 1,984 paragraphs. `eval/chunking_eval.py` chunks each one both ways into a separate local table, `chunks_experiment`, and runs exact dense search on it (no index). Paragraph chunking packs blocks into chunks of up to 200 words. Fixed chunking uses 100-word windows with 20 words of overlap.

**Answer set.** `eval/questions.jsonl`, built by `scripts/build_eval_questions.py`: 45 questions.

| Source | Type | Questions | Expected |
| --- | --- | ---: | --- |
| HotpotQA | bridge | 15 | answer |
| HotpotQA | comparison | 10 | answer |
| NovaPay | simple | 5 | answer |
| NovaPay | multi_doc | 5 | answer |
| NovaPay | contradiction | 5 | flag the conflict |
| NovaPay | unanswerable | 5 | insufficient |

The 25 HotpotQA questions are the first 15 bridge and 10 comparison questions of a seed-42 shuffle of the validation split. The 20 NovaPay questions are in `eval/company_questions.jsonl`. Each names its gold documents by file name, and some also list "acceptable" documents that state the same fact. The answer key for the NovaPay corpus is `eval/company_scenario.md`.

Each question was answered once in each mode: 90 answers. All 90 were saved with model `gemini-3.5-flash-lite` and database `.env` (the local database), between 21:24 and 21:45 UTC on 2026-10-28 (`saved_at` in `eval/results/answers_raw.jsonl`). ## 2. Metrics

| Metric | Definition | How |
| --- | --- | --- |
| Recall@k | Share of the gold documents among the titles of the first k results. The retrieval eval uses the first k chunks; the chunking and answer evals first collapse results to distinct documents. | automatic |
| MRR | 1 / rank of the first gold document, averaged over questions. Depth: top 10 chunks in the retrieval eval, top 30 chunks in the chunking eval, first 8 documents in the answer eval. | automatic |
| Evidence recall | Recall over every document the mode saw (agent mode: all its searches). | automatic |
| Exact match | 1 if the answer equals the gold answer after SQuAD-style normalization (lowercase, no punctuation, no a/an/the), with `[S#]` markers removed. HotpotQA only. | automatic |
| Token F1 | Word-overlap F1 between the normalized answer and gold answer. HotpotQA only. | automatic |
| Gold answer in the answer | 1 if the normalized gold answer appears in the answer as whole words. HotpotQA only. | automatic |
| Citation accuracy | Cited documents that are gold (or acceptable) ÷ all cited documents. Each document counts once. Answers that cite nothing are not scored. | automatic |
| Abstention | Status `insufficient`. Counted on the 5 unanswerable questions, and as a mistake on the 40 answerable ones. | automatic |
| Conflict reported | The `conflicts` list is not empty. It doesn't check that it is the right conflict. | automatic |
| Correctness | correct / partly correct / wrong, against the reference answer. NovaPay questions only. | by hand |
| Contradiction flagged | yes / no, on the 5 contradiction questions. | by hand |

## 4. What the numbers say

**Dense vs hybrid.** On these 200 HotpotQA questions, hybrid search is not better at the top of the list. Recall@5 is almost the same (0.728 vs 0.720). Dense only is better at Recall@2 (0.618 vs 0.527) and MRR@10 (0.870 vs 0.827). Hybrid is better only at Recall@10 (0.818 vs 0.787). It is also much slower: 346 ms per query against 23 ms. All 200 questions are HotpotQA, so this says nothing about the NovaPay documents, where exact IDs and names may matter more. I didn't run this comparison on NovaPay. <!-- EDIT: why you kept hybrid as the default anyway, or whether you plan to change it -->

**Paragraph vs fixed chunking.** The difference is small: Recall@5 0.882 vs 0.875, MRR 0.949 vs 0.942. Most HotpotQA paragraphs are short. Paragraph chunking split only 61 of the 1,984 paragraphs, so almost every paragraph stayed one chunk; fixed chunking split 664. Paragraph chunking needs fewer chunks (2,049 vs 2,779). This subset has no long documents, so it can't show how the chunkers differ on them. The search space here is 1,984 paragraphs, not the full collection, so these numbers can't be compared with table (a).

**Simple vs agent.**

- Retrieval: agent mode's Recall@5 is lower (0.650 vs 0.725), but its evidence recall is higher (0.838 vs 0.762). The first documents it sees are worse than simple mode's top 5, but its later searches find more of the gold documents.
- HotpotQA answers: the gold answer appears in 0.880 of agent answers against 0.560 of simple answers. Token F1 is low in both (0.189 vs 0.126) because the answers are full sentences, and exact match is 0 in both for the same reason.
- Abstention: simple mode wrongly abstained on 8 of 40 answerable questions, agent mode on 1. This is the biggest difference between the modes. Both abstained correctly on only 3 of 5 unanswerable questions.
- Citations: about the same (0.964 vs 0.962).
- Conflicts: simple mode reported a conflict on 4 of 5 contradiction questions, agent mode on 3 of 5. Neither reported a conflict on the 35 other answerable questions.
- NovaPay hand grades: nearly the same (14 / 5 / 1 vs 13 / 7 / 0). With 5 questions per type, a difference of one answer is 20 points, so I don't read anything into it.
- Cost: agent mode takes 3.6 s per question on average against 1.3 s, and uses 2.8 rounds on average. The fallback ran once.

## 5. Error analysis

The full notes are in [`eval/results/error_analysis.md`](../eval/results/error_analysis.md). 29 of the 90 answers failed at least one check (gold answer not in the answer, Recall@5 = 0, a wrong abstention, a missed conflict, citation accuracy below 1, or a hand grade of partly correct or wrong). From those, 10 answers were picked that each show one failure type clearly, and sorted into four groups. The counts below are out of those 10, not out of all 29. Claude Code drafted these notes (see the AI usage report). <!-- EDIT: say what you checked yourself in the notes -->

### Retrieval miss (3 of 10)

- **Example:** `co_conflict_01`, agent mode. It searched once and answered. The 5 chunks included 3 from the same postmortem and none from the finance memo. It said 1,284 and flagged no conflict; the memo's 1,317 was never seen.
- **Likely cause:** simple mode searches once with the whole question. Keyword search matches any single word, so parts of names pull in other pages (Lil Wayne for "Wayne Black" in `hp_comparison_07`). Agent mode gets only 5 chunks per search, and the prompt tells it to stop once the passages answer the question.
- **What I'd improve:** return 8 chunks per agent search with at most 2 from the same document. For questions about a count, amount or time, force one more search for other sources of that number.

### Wrong answer despite good sources (2 of 10)

- **Example:** `hp_comparison_10`, simple mode. Both gold pages were retrieved (ranks 2 and 7). It said Manchester Orchestra's member count "is not stated", but that page names four members. Agent mode got it right.
- **Likely cause:** the prompt says "Never guess", and the model seems to treat anything it has to work out itself as missing. When it does work something out, nothing checks it: in `co_multi_05` it tied actions AI-3 and AI-4 to CHG-0419, though they address neither change.
- **What I'd improve:** one prompt line saying that counting, comparing or subtracting values from the sources is allowed if the step is shown. For matching questions, a rule to quote the sentence that links each pair, or say the link is not stated.

### Bad citation (2 of 10)

- **Example:** `co_simple_01`, simple mode. The date was right (17 March 2026), but it also cited the incident report, which has no deploy date. Citation accuracy 0.33.
- **Likely cause:** `finalize()` only checks that each `[S#]` id exists. Nothing checks that the cited chunk says what the sentence claims. `finalize()` also withholds the whole answer when no valid marker is left, which turned `hp_bridge_09` (agent) into `insufficient` with both gold pages in hand, and the withheld text is not saved. Some low scores are not real errors: the cited page supports the sentence but isn't on the gold list (`hp_comparison_04` simple, `hp_comparison_07` and `co_multi_05` agent).
- **What I'd improve:** before withholding, ask the model once more to add markers, and save the withheld text. Drop a citation when a date or number in the sentence doesn't appear in the cited chunk.

### Wrong abstention (3 of 10)

- **Example:** `co_multi_04`, simple mode. The right runbook was at rank 6, but it came from keyword search only, so it had no dense score. The best dense score in the top 8 was 0.597 ("Fake field goal"), below 0.62, so the gate blocked the question. Agent mode answered correctly.
- **Likely cause:** two different steps. The gate looks only at dense similarity; in all three gate blocks that had a gold page in the top 8 (`co_multi_04`, `hp_comparison_07`, `hp_bridge_13`), that page came from keyword search only. And the LLM sets the status itself and errs both ways: it gave up in `hp_bridge_10` with both facts in front of it, and on unanswerable questions (`co_none_01`, `co_none_03`) it says `partial` when it finds related background, even though its own text says the fact is missing.
- **What I'd improve:** gate on the fused hybrid score, or let a keyword-only chunk in the top 3 pass. Add a prompt rule that related background doesn't make an answer `partial`, and a check that sets `insufficient` when the answer says the sources don't give the fact.

## 6. Limits of this evaluation

- **Small sample.** 45 answer questions, and only 5 per NovaPay type, so one answer moves a rate by 20 points. The 200 retrieval questions are all HotpotQA.
- **One grader, and the grades were drafted by AI.** Claude drafted the NovaPay grades and the grading rule. TODO(Nika): how you reviewed them.
- **AI-written company corpus.** The NovaPay documents are synthetic and were written with AI, and Claude drafted the 20 NovaPay questions. Questions and documents may share wording that real questions wouldn't. <!-- EDIT: anything you did to reduce this -->
- **Threshold tuned on the same data.** I picked the gate threshold with `scripts/eyeball_threshold.py`, on 5 answerable and 5 off-topic questions. One of the 5 answerable ones ("At what time was incident INC-2026-031 resolved?") is eval question `co_simple_03`, and two more are about the same incident. The script's output isn't saved. TODO(Nika): the lowest answerable and highest off-topic scores it printed.
- **LLM non-determinism.** Each question was asked once per mode. `app/llm.py` doesn't set a temperature, so the model's default is used, and a rerun can give different answers. The small counts (3/5, 4/5) are the most likely to move.
- **Local database, not Neon.** All runs used the local database. The live app uses Neon. TODO(Nika): confirm Neon holds the same documents.
- **Titles, not passages.** Retrieval metrics and citation accuracy compare document titles. A cited NovaPay document counts as correct even if the cited chunk is not the one with the fact.
- **Exact match is not useful here.** The answers are full sentences, so it is 0 by design. "Gold answer in the answer" is the better signal for HotpotQA.

## 7. How to reproduce

All commands run from the repo root, with the database loaded as in the README.

```
python -m eval.retrieval_eval --limit 10      # quick check, saves nothing
python -m eval.retrieval_eval                 # writes eval/results/retrieval.md
python -m eval.chunking_eval                  # local database only; prints the chunking table
python -m scripts.build_eval_questions        # writes eval/questions.jsonl (no LLM calls)
python -m eval.answer_eval run --limit 2      # smoke test: first 2 questions, both modes
python -m eval.answer_eval run                # every (question, mode) pair not saved yet
python -m eval.answer_eval score              # metrics from the saved answers (no LLM, no database)
```

- `answer_eval run` makes many LLM calls. The saved run made at least 167: 41 in simple mode (4 of the 45 questions stopped at the gate), 125 agent rounds and 1 fallback, counted from `eval/results/answers_raw.jsonl`. Retries aren't logged, so the real number can be higher. The saved answers span 21:24 to 21:45 UTC (`saved_at`).
- Raw answers are appended to `eval/results/answers_raw.jsonl` as they arrive, one line per (question, mode). After a crash or a stop, the same command carries on with the pairs that are missing or failed.
- `score` writes `answer_scores.jsonl`, `answers.md` and `company_answers_for_grading.md` in `eval/results/`.
- **Careful:** `score` rewrites `company_answers_for_grading.md` with empty grades and rewrites `answers.md` without the hand-grade table. `retrieval_eval` rewrites `retrieval.md` without the chunking table. Copy those files first if you rerun.
- Set `MIN_DENSE_SIMILARITY` in `.env` to the same value as the saved run, or simple mode's gate will behave differently.
